# EventResolver refactor: field-level auto-derivation → full registry derivation

## Before

`EventResolverImpl.getTypedEvent` was a ~290-line `match` over ~45 event names. Every branch repeated the same shape:

```scala
case "OrderAdded" =>
  OrderAdded(
    orderId           = NaymsDiamond.getOrderAddedEventFromLog(obj).orderId,
    maker             = NaymsDiamond.getOrderAddedEventFromLog(obj).maker,
    sellToken         = NaymsDiamond.getOrderAddedEventFromLog(obj).sellToken,
    sellAmount        = NaymsDiamond.getOrderAddedEventFromLog(obj).sellAmount,
    sellAmountInitial = NaymsDiamond.getOrderAddedEventFromLog(obj).sellAmountInitial,
    buyToken          = NaymsDiamond.getOrderAddedEventFromLog(obj).buyToken,
    buyAmount         = NaymsDiamond.getOrderAddedEventFromLog(obj).buyAmount,
    buyAmountInitial  = NaymsDiamond.getOrderAddedEventFromLog(obj).buyAmountInitial,
    state             = NaymsDiamond.getOrderAddedEventFromLog(obj).state,
  )
```

Two kinds of duplication compounded:
1. **Dispatch boilerplate** — `case "X" => ... case _ => Unsupported(name)`.
2. **Per-event constructor boilerplate** — for most events, the response and the case class share field names, so each branch is just "for every field, copy it".

## After

The whole registry is generated by a macro:

```scala
private val resolvers: Map[String, LogObject => TypedEvent] =
  AutoMap.deriveResolvers[TypedEvent, NaymsDiamond] ++ customResolvers
```

`customResolvers` is a single entry — `FeeScheduleAdded` — because it zips two parallel arrays into `List[FeeReceiver]`, a real shape transformation. Everything else is derived from the case-class declarations.

Adding a new event is now: declare the case class with ABI-matching field names. The macro picks it up automatically. Mistakes (typo in a field name, missing ABI getter) become **compile errors** at the macro call site.

## `AutoMap.scala`

The file exposes two macros and one marker trait.

### `from[E, T]` — field-level derivation

```scala
inline def from[E, T <: Product](e: E): T = ${ fromImpl[E, T]('e) }
```

Used for one-off conversions. Given a source `E` and a target `T`, it generates a `new T(...)` call where each argument is `e.<fieldName>` (direct access if types match) or `conv(e.<fieldName>)` (where `conv` is a summoned `given Conversion[fromType, toType]`).

### `deriveResolvers[Sum, Owner]` — registry derivation

```scala
inline def deriveResolvers[Sum, Owner]: Map[String, LogObject => Sum] =
  ${ deriveResolversImpl[Sum, Owner] }
```

This is the one that replaces ~290 lines of hand-rolled code. At compile time it:

1. **Enumerates the sealed children of `Sum`** via `TypeRepr.of[Sum].typeSymbol.children`. For `Sum = TypedEvent`, that's every `case class X(...) extends TypedEvent` in the file.
2. **Skips children marked with `NoAutoDerivation`.** That's how `Unsupported` and `FeeScheduleAdded` opt out — they mix in the marker trait.
3. **For each remaining case class `C`**, derives `getterName = s"get${C.name}EventFromLog"` and looks it up on `Owner`. Java statics live on the synthetic companion module, so the macro searches both `Owner` and `Owner.companionModule`. If neither has the method, the macro **aborts compilation** with a message naming the missing method and the case class — no silent runtime surprises.
4. **Extracts the response type** from the getter's signature (`MethodType.resType`).
5. **Emits a `LogObject => Sum` lambda** by hand-building the AST:
   ```
   (obj: LogObject) => {
     val response = Owner.getter(obj)
     new C(response.field1, conv(response.field2), ...)
   }
   ```
   The field-level mapping is the same `buildProduct` helper used by `from`, so the same Conversion-summoning rules apply.
6. **Bundles all `(caseName, lambda)` pairs into `Map(... *)`**.

### Lambda construction via reflection

Instead of using a quoted lambda expression (where bridging type variables across splices gets fiddly), the macro builds the lambda directly:

```scala
Lambda(
  owner = Symbol.spliceOwner,
  tpe   = MethodType(List("obj"))(_ => List(TypeRepr.of[LogObject]), _ => sumRepr),
  rhsFn = (sym, params) => {
    val objTerm    = params.head.asInstanceOf[Term]
    val getterCall = Apply(Ref(getterSym), List(objTerm))
    buildProduct(childRepr, responseRepr, getterCall).changeOwner(sym)
  }
).asExprOf[LogObject => Sum]
```

This sidesteps the awkward "how do I refer to the lambda parameter inside a nested splice" problem and gives precise control over the generated tree.

### `NoAutoDerivation`

```scala
trait NoAutoDerivation
case class Unsupported(topic: String) extends TypedEvent with NoAutoDerivation
case class FeeScheduleAdded(...) extends TypedEvent with NoAutoDerivation
```

A one-word opt-out at the case-class declaration site. The macro skips anything that extends it. `Unsupported` opts out because it's the fallback (no on-chain event); `FeeScheduleAdded` opts out because its shape genuinely differs from its ABI response.

### `buildProduct` — shared between both macros

A small private helper inside `AutoMap` that, given a target case class type and a source type, emits the constructor-call AST that maps each named field. Used by `fromImpl` (single conversion) and `deriveResolversImpl` (inside each generated lambda).

For each target field:
- If types match exactly → emit `Select(sourceTerm, sourceField)`.
- If types differ → look up a `given Conversion[srcType, tgtType]` via `Implicits.search`; emit `conv(sourceField)` if found; **compile error** if not.

All checks happen at compile time, so the runtime code is plain field access + lambda calls. No runtime reflection — important because the project targets GraalVM native-image, which is hostile to reflective access.

## Resulting resolver

```scala
case class EventResolverImpl() extends EventResolver {
  // ...eventMap and getName unchanged...

  import NaymsDiamond.*

  private val customResolvers: Map[String, LogObject => TypedEvent] = Map(
    "FeeScheduleAdded" -> { obj =>
      val e = getFeeScheduleAddedEventFromLog(obj)
      val feeReceivers = e.feeSchedule.receiver.getValue.asScala
        .zip(e.feeSchedule.basisPoints.getValue.asScala)
        .map((r, bp) => FeeReceiver(r, bp))
        .toList
      FeeScheduleAdded(entityId = e.entityId, feeType = e.feeType, feeReceivers = feeReceivers)
    }
  )

  private val resolvers: Map[String, LogObject => TypedEvent] =
    AutoMap.deriveResolvers[TypedEvent, NaymsDiamond] ++ customResolvers

  def getTypedEvent(obj: LogObject): Task[TypedEvent] = ZIO.attempt {
    val name = getName(obj.getTopics.get(0))
    resolvers.get(name).fold[TypedEvent](Unsupported(name))(_(obj))
  }
}
```

~290 lines of `match` → ~15 lines of registry. Verified at runtime: the macro produces 44 auto-derived handlers, merged with the 1 custom override, for 45 total resolver entries — exactly the set of events declared in `TypedEvent`'s sealed hierarchy.

## What "adding a new event" now looks like

1. Add the case class with ABI-matching field names:
   ```scala
   case class MyNewEvent(foo: Bytes32String, bar: BigInt) extends TypedEvent
   ```
2. If `MyNewEvent`'s field types don't already have a `given Conversion`, add one (rare — most coverage is already there).
3. Done. The macro picks it up at the next compile. If `getMyNewEventEventFromLog` doesn't exist on `NaymsDiamond`, you get a clear compile error at the resolver call site.

No edit to the resolver. No `case "MyNewEvent" =>`. No `*_EVENT` import (still needed only for the `eventMap` topic-hash → name lookup; could be macro-derived in a future pass).

## Trade-offs

- **Pro**: a 45-event resolver becomes a one-liner. Every event is treated identically by construction.
- **Pro**: compile-time safety — typos and missing getters fail fast at the registration site.
- **Pro**: no runtime reflection, native-image friendly.
- **Con**: the macro is real Scala 3 quoted-reflection code (~100 lines). Anyone changing it has to understand `quotes.reflect`. But that's amortized — the macro is read rarely, used everywhere.
- **Con**: implicit coupling between case-class names and ABI getter method names. If the contracts library renames `getX` to `getY`, you'd get a compile error pointing at the offending case class. That's the system working as intended, but worth being aware of.
